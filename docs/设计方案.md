## 1. 项目概述

### 1.1 目标

为几个人（家庭/好友小圈子）搭建一套**私有即时通讯系统**，支持 iPhone、iPad、安卓、Windows 四端互发消息。服务端运行在已有的上海 VPS 上，数据完全自持，不依赖任何公有聊天服务，不上架任何应用商店。

### 1.2 非目标（v1 明确不做）

- 音视频实时通话
- 群聊功能（但架构预留，见 §4.7）
- 端到端加密（服务器可见消息内容，全链路 TLS 保护传输）
- 公开注册、多租户、高并发设计（用户规模 ≤ 10 人）

### 1.3 核心约束（决定架构的三个事实）

1. **iOS 不上架**：采用免费 Apple ID 自签 + 自动续签（§7），代价是自家 App 拿不到 APNs 系统推送，需要「推送铃」方案补位（§6）。
2. **维护者不写代码**：由 AI 负责开发和后续维护，因此全系统追求**组件少、结构简单、可文档化**，避免复杂第三方协议生态。
3. **纯 IP 访问**：VPS 不挂域名，用自签证书 + 客户端内置锁定（§8），不涉及 ICP 备案。

## 3. 总体架构

```
                       ┌────────────────────── 上海 VPS（Linux）──────────────────────┐
                       │                                                              │
   iPhone / iPad ──────┼──►  quickconect-server（Go 单二进制，监听 :8443, TLS）        │
   Android 手机 ───────┤        ├── REST API：登录 / 拉取历史 / 上传下载媒体            │
   Windows 电脑 ───────┤        ├── WebSocket：实时收发消息、心跳、在线状态             │
        │              │        ├── SQLite：用户、设备、会话、消息、媒体索引            │
        │              │        └── 媒体目录：/var/lib/quickconect/media/              │
        │              │                                                              │
   ntfy App ───────────┼──────► ntfy.sh（外部免费服务，充当「推送铃」）                  │
   (iOS/安卓均装)      │           ▲ 服务端检测到离线用户有新消息时，发布节流后的空 ping   │
                       │             ntfy.sh 经 APNs(iOS)/FCM(安卓) 唤醒 ntfy App       │
                       └──────────────────────────────────────────────────────────────┘

  客户端在 App 存活期间走自家 WebSocket（体验最佳）；App 被系统挂起/杀掉后由 ntfy 铃兜底。
```

组件清单（全部需要部署/维护的东西）：

| 组件 | 位置 | 说明 |
|------|------|------|
| quickconect-server | VPS | 自研 Go 服务端，systemd 托管 |
| Flutter App（四端） | 各设备 | 自研客户端，同一份代码 |
| ntfy App | 各手机 | App Store / GitHub APK 安装，现成软件，零维护 |
| SideStore | 各 iOS 设备 | 自签续签工具，现成软件 |
| 证书（自签 CA） | VPS + 客户端内置 | 一次性生成，脚本化 |

## 4. 服务端设计

### 4.1 技术选型

- **Go + SQLite**（WAL 模式），编译为单个静态二进制 `quickconect-server`，无任何外部服务依赖。
- 一个端口（默认 **8443/TCP**）同时服务 HTTPS REST 与 WebSocket 升级。
- 配置文件 `/etc/quickconect/config.yaml`；数据全部在 `/var/lib/quickconect/`（一个 .db 文件 + 一个媒体目录）。

### 4.2 API 概览

REST（均需 Bearer Token，`/healthz` 除外）：

```
POST /api/auth/login        登录（用户名+密码+设备名）→ 返回设备 token
POST /api/auth/logout       注销当前设备 token
GET  /api/me                当前用户信息
GET  /api/users             用户名册（小圈子：全员即联系人）
GET  /api/conversations     会话列表（含最后一条消息 + 未读数）
GET  /api/conversations/{id}/messages?after_seq=N&limit=M   增量拉取消息
POST /api/conversations/{id}/messages      发消息
POST /api/media             上传媒体（multipart 流式落盘）
GET  /api/media/{id}        下载媒体（?thumb=1 取缩略图）
```

WebSocket `wss://IP:8443/api/ws`：

- 连接时带 token 鉴权；客户端每 30s 发心跳，服务端据此维护在线状态。
- 服务端推送事件：`message.new`（新消息）、`message.ack`（送达确认）、`conversation.update`（未读数变化）。

消息 JSON 结构（`type` + `payload`）：

```json
{"type":"text",    "payload":{"text":"你好"}}
{"type":"image",   "payload":{"media_id":"...","thumb_media_id":"...","w":1080,"h":810}}
{"type":"file",    "payload":{"media_id":"...","name":"报告.pdf","size":238400}}
{"type":"voice",   "payload":{"media_id":"...","duration_ms":5300}}
{"type":"sticker", "payload":{"pack_id":"...","sticker_id":"..."}}
```

### 4.3 数据模型（SQLite 表）

```sql
users(id, name, display_name, password_hash, created_at)
devices(id, user_id, push_topic, platform, device_name,
        token_hash, last_seen_at, created_at)
conversations(id, type, dm_key, created_at)
    -- type: 'dm' | 'group'(预留)；dm_key = "uidA:uidB"（按双方 id 排序）防重复建会话
conv_members(conv_id, user_id, last_read_seq, joined_at, PRIMARY KEY(conv_id, user_id))
messages(id, conv_id, seq, sender_id, type, payload_json,
         client_msg_id, created_at,
         UNIQUE(conv_id, seq), UNIQUE(sender_id, client_msg_id))
media(id, owner_id, kind, mime, size_bytes, path, created_at)
```

要点：

- `messages.id` 使用 ULID（时间有序、全局唯一）。
- `UNIQUE(sender_id, client_msg_id)` 实现**发送幂等**：弱网重试不会产生重复消息。
- `UNIQUE(conv_id, seq)` 保证会话内消息**严格有序**，这是多端同步的基石。

### 4.4 消息可靠性与多端同步

这是自研服务端最核心的机制，规则简单且经过验证：

1. **会话内单调序列号 `seq`**：每条消息入库时取该会话内 `max(seq)+1`。
2. **设备游标**：每台设备记录自己「已同步到哪条」（`last_read_seq` 的同步位）。
3. **实时通道**：在线时 WebSocket 推送新消息。
4. **对账兜底**：任何重连/打开 App/心跳超时后，客户端用游标调 `messages?after_seq=` 补齐缺口，保证**不丢、不重、不乱序**。
5. **发送队列**：客户端发出的消息先落本地库（状态=发送中），收到服务端 ack 后标记成功；失败自动重试，`client_msg_id` 保证幂等。

### 4.5 媒体文件（图片 / 文件 / 语音）

- 上传：`POST /api/media` 流式写入磁盘（路径按内容哈希分桶），不占内存；服务端不做转码。
- 图片：客户端上传原图 + 客户端生成缩略图一并上传，消息体引用两者；聊天页加载缩略图，点开加载原图。
- 语音消息：客户端录制 **AAC (.m4a)，单声道 24kbps**，一段 60 秒语音约 180KB，对 VPS 带宽友好；消息体含时长。
- 文件：默认**单文件上限 100MB**、**每用户总配额 10GB**（config.yaml 可调）；超限拒绝并提示。
- 服务端定期清理「无任何消息引用的孤儿媒体」（每日任务）。

### 4.6 表情包设计

- 表情包 = 一组图片 + 一个 `manifest.json`（包名、作者、贴纸 ID 列表）。
- v1 方案：**内置包**随 App 分发（零服务端逻辑）+ **自定义包**（把整包打成一个 zip 上传为普通媒体，导入后存本地）。服务端不建表情包专表，保持简单。
- 面板 UI：聊天输入框表情键 → 包列表 → 网格选择 → 以 `sticker` 消息发送（原图质量，无边框气泡展示）。

### 4.7 群聊预留

数据模型从第一天就是通用的「会话-成员」结构：1 对 1 就是两个成员的会话。将来加群聊只需：

1. 打开 `conversations.type='group'` 的创建入口；
2. 发消息的扇出循环从「对方」改为「遍历成员」；
3. UI 加成员管理页。

服务端核心收发逻辑零改动，**不会推翻重来**。

### 4.8 推送铃集成（ntfy.sh）

选型说明（相较讨论稿的一处简化）：**不再在 VPS 上自托管 ntfy 服务端，直接使用 ntfy.sh 公共服务**。原因：自托管方案中 iOS 的推送同样必须经 ntfy.sh 转发（iOS 上只有商店版 ntfy App 持有 APNs 资格），自托管只对安卓有边际收益，却多一个常驻服务和一个自签证书对接问题。直连模式下 ntfy App 只与 ntfy.sh 通信，证书、可用性全部由官方托管，部署面最小。

工作方式：

1. **设备注册**：每台设备登录时，服务端生成专属 topic：`qc_` + 32 位随机串（不可猜，即访问凭证）。
2. **订阅**：客户端「设置 → 推送铃」页展示 `https://ntfy.sh/qc_xxx` 订阅链接/二维码，用户在 ntfy App 中一键订阅（每台设备一次）。
3. **发布**：服务端检测到某用户**没有活跃 WebSocket 连接**时产生新消息 → 触发节流合并（同一收件人 30 秒窗口内只发一条）→ `POST https://ntfy.sh/<topic>`，内容仅含标题「新消息」与正文「您有 N 条新消息」（**不含消息内容和发送者**，元数据最小化；可在配置中改为附带发送者昵称）。
4. **唤醒**：ntfy.sh 经 APNs（iOS）/ FCM（安卓）推给该设备的 ntfy App → 用户看到通知 → 打开 QuickConect 对账补齐。

服务端按令牌桶全局限流，个人规模距 ntfy.sh 免费额度余量极大。

## 5. 客户端设计（Flutter）

### 5.1 工程结构

```
quickconect/
├── server/            Go 服务端
├── app/               Flutter 客户端（四端共用）
│   ├── lib/core/      API 客户端、WebSocket、证书锁定、本地数据库(Drift/SQLite)
│   ├── lib/pages/     登录、会话列表、聊天页、媒体查看、设置
│   └── lib/widgets/   气泡、图片九宫格、语音条、表情包面板
└── deploy/            部署脚本、证书生成脚本、备份脚本、systemd 单元
```

### 5.2 界面模块

- **登录页**：用户名 + 密码（账号由管理员在服务端创建，无注册入口）。
- **会话列表**：按最新消息排序，头像 + 昵称 + 未读角标（红点数字）。
- **聊天页**：气泡布局；图片网格/点开大图；语音条（按住说话、上滑取消、点播）；表情包面板；发送失败红色感叹号（点击重试）；消息按 seq 严格有序展示。
- **媒体查看器**：大图缩放、文件下载分享。
- **设置页**：推送铃订阅二维码、保活开关（仅 iOS）、通知偏好、深色模式、退出登录。

### 5.3 本地存储与离线

- 本地 SQLite 缓存全部消息与缩略图：打开 App 秒进历史，无网可看缓存。
- 待发队列：断网时消息排队，恢复后自动补发。
- 首次登录全量拉取历史，此后增量对账（§4.4）。

### 5.4 各平台差异

| 平台 | 关键点 |
|------|--------|
| iOS/iPadOS | 后台模式声明 `audio`（保活用）；App 存活期用本地通知横幅 + 图标角标；注册 BGAppRefresh 做不定期后台对账；可选静音保活开关（见 §6） |
| Android | 可选前台服务（常驻通知「QuickConect 在线」）保持长连接；引导用户关闭电池优化（白名单教程）；国产行机额外装 ntfy 兜底 |
| Windows | 同一代码库；托盘图标 + 关闭最小化到托盘；开机自启可选；录音/播放经 Flutter 桌面插件支持 |

## 6. 通知与推送策略（按平台）

核心思路：**App 活着靠自家长连接，App 死了靠 ntfy 铃**，两层叠加逼近原生推送体验。

| 场景 | iOS/iPadOS | Android(GMS) | Android(国产无GMS) |
|------|-----------|--------------|-------------------|
| App 前台 | 页面内实时 + 本地横幅 | 同左 | 同左 |
| App 后台存活 | 长连接推送 → 本地横幅+角标；可选静音保活延长存活 | 同左（前台服务加持更稳） | 前台服务长连接 → 实时横幅 |
| App 被挂起/杀掉 | **ntfy 铃**（APNs）秒级通知 | **ntfy 铃**（FCM） | **ntfy 铃**（ntfy GitHub 版自带长连接）+ 打开对账兜底 |
| 偶发全灭 | 打开 App 秒级全量对账，不丢消息 | 同左 | 同左 |

iOS 补充说明：

- **红点/横幅的实时边界**：App 退后台后约有几十秒宽限期可继续收发；之后系统挂起，红点在 BGAppRefresh 被择机唤醒时「迟到纠正」。
- **保活开关（默认关）**：后台播放静音音频阻止挂起，红点横幅全部实时；代价是耗电增加、偶发被杀（回到兜底层）。做成每设备自己的开关。
- TrollStore 可用的设备（待确认 iOS 版本）可永久签名，且仍可正常用 ntfy 铃。

## 7. iOS 分发与签名方案

### 7.1 方案与流程

免费 Apple ID 签名的硬性限制：**7 天有效期、每设备 3 个自签 App 上限、无 APNs**。本方案在限制内工作：

1. **首次安装（每台设备一次，需 Windows 电脑 + USB）**：
   - 在电脑上用 Sideloadly/AltServer 安装 **SideStore**（免签续签工具）；
   - SideStore 内登录专用 Apple ID（建议注册一个专用账号，不用个人 iCloud）；
   - 之后一切在设备上完成：SideStore 下载我们的 IPA 并签名安装，SideStore 自身也会自续签。
2. **日常续签（自动）**：SideStore 通过设备内 VPN 通道定期自动续签我们的 App，正常情况无感。
3. **偶发失败（预期内）**：iOS 大版本更新或 Apple 周期性撤签时，重连电脑走一遍首装流程即可（教程会写清步骤）。
4. **App 配额**：每设备占用 2 个名额（SideStore + QuickConect），上限 3 个，无冲突。

### 7.2 iOS 构建流水线（重要：构建需要 macOS）

Flutter 的 iOS 产物必须在 macOS 上构建，而本项目的电脑是 Windows、服务器是 Linux。方案：

- **GitHub Actions macOS 云构建**：推送代码/打 tag → 云端构建出 IPA → 从 Windows 电脑下载 → 传给 SideStore 安装。
- 免费额度：私有仓库每月约可构建 8–10 次（macOS 计费 10 倍），开发期够用；若不够可将仓库设为公开（代码无敏感信息，证书和密码均在 VPS 与设备上，不在仓库内）。

### 7.3 升级路径

任何时候购买 Apple 开发者账号（¥688/年）即可获得：签名一年一次 + APNs 真推送（届时自家 App 直接接推送，ntfy 铃退役为可选）。**架构无需任何改动**，这是本方案刻意保留的后门。

## 8. 证书、安全与账号

- **自签 CA**：部署时脚本生成私有根证书（ECDSA P-256），服务端证书绑定 VPS 的 IP。**四端客户端内置 CA 指纹锁定**——只有我们自己的 App 信任它，无需在任何系统安装描述文件，浏览器也无法访问。
- **传输**：TLS 1.2+，仅 8443 一个对外端口；防火墙只放行该端口与 SSH。
- **鉴权**：登录返回每设备独立 token（256 位随机，库内只存哈希），可单独吊销（换手机/丢机场景）；登录接口限速防爆破。
- **账号**：管理员在 VPS 上用 CLI 创建（`quickconect adduser`），无自助注册，服务面对公众为零。
- **隐私边界**：消息内容仅存于自家 VPS；经过外部服务的只有 ntfy 铃的「计数空 ping」（不含内容与发送者）。
- **合规**：私人小范围自用、无公开服务、无域名网站，属低风险个人部署；不对公众提供服务。

## 9. VPS 部署与运维

```
/opt/quickconect/quickconect-server     二进制
/etc/quickconect/config.yaml            配置（端口/限额/ntfy开关）
/var/lib/quickconect/quickconect.db     数据库（WAL）
/var/lib/quickconect/media/             媒体文件
```

- **进程**：systemd 单元 `quickconect.service`，开机自启、崩溃自动重启。
- **备份**：每晚 cron：`sqlite3 .backup` + 打包媒体目录到 `/var/backups/`；可选 rclone 同步到外部存储（待确认）。
- **监控**：`GET /healthz` 无鉴权健康检查；日志走 journald。
- **升级**：替换二进制 + `systemctl restart`，停机 < 2 秒；数据库有 schema 版本表，升级脚本自动迁移。
- **资源预估**：几人规模常驻内存 < 100MB，CPU 可忽略；瓶颈仅在带宽（国内小水管 VPS 传大文件慢，已用 100MB 上限与 AAC 低码率语音对冲）。

## 10. 开发阶段规划

垂直切片优先：先让两端互发文字跑通全链路，再横向铺功能。

| 里程碑 | 内容 | 预估 | 验收标准 |
|--------|------|------|----------|
| M0 骨架 | 服务端（鉴权/会话/消息/WS）部署上 VPS；移动端登录+会话列表+文字私聊；证书锁定 | 第 1 周 | 手机↔电脑实时互发文字；断网重连自动补齐、不丢不重 |

| M2 推送 | ntfy 铃全平台接入、iOS 保活开关+后台刷新+角标、安卓前台服务与白名单引导 | 第 3 周 | App 被杀后 iOS/安卓都能收到 ntfy 通知 |
